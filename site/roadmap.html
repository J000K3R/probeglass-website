Roadmap

What is new, what is next, and what came before

ProbeGlass is a small product on purpose, so this page is short on purpose. The present comes first, then what is next — dates are not promises, and the order is what the design already supports cheaply. The history of what each release added is at the end. The documentation's roadmap is the source of truth, and it mirrors the one in the repository.

Now

0.2.2 is released, and ghcr.io/j000k3r/probeglass:0.2.2 is the tag to pin — :dev follows the branch under development. One container, one SQLite file, and the same small dependency set it has always had.

On :dev now

Six more sensor types

An SSH banner, SMTP and IMAP greetings, a UDP port, an ICMP TTL/hop probe and an HTTP redirect chain that reports where it ends. Each is the smallest exchange that answers its question.

On :dev now

A sensor editor that chooses

The type is a grouped, searchable chooser; group, place, tag and dependency fields use the same picker, and every option is a visible chip instead of a dropdown. The dependency list shows each sensor's state, and groups are arranged by dragging their rows in Settings.

On :dev now

Gotify, the seventh channel

The self-hosted push server a homelab already runs: an address and an app token, a priority that follows the event or is set on the channel.

On :dev now

Example data you can see

Four brand pictures, two maintenance windows and a week of invented history, so the first dashboard is neither empty nor a wall of grey.

Released in 0.2.2

Dependencies, symbols, one scale

One outage behind a parent is one incident. A sensor, a place and a group heading can wear a symbol — ours, yours, or one searched for online — and the dashboard's measurements are two scales instead of fifteen type sizes.

Before that

0.2.0 and 0.2.1

Maintenance windows, German as a second language, and a card that says when its sensor is inside a window. The container became the only thing that ships.

Nothing here is a subscription feature. Everything is in the image you pull, under the MIT licence, with no tier above it.

Next

0.2.x

Ordered by value per unit of work.

  • Escalation. A second channel that only fires when an incident is still open after N minutes.
  • Import and export. A JSON round-trip of sensors and channels, so a configuration can be versioned or moved — the export half already ships as the Backup and restore panel; what is left is a documented file format and a dry run before an import is applied.

Later

0.3.x and beyond
  • A /metrics endpoint, so a homelab that already runs a monitoring stack can scrape ProbeGlass instead of duplicating the checks it already makes.
  • A public status page on its own path and its own token, safe to share outside the LAN.
  • SLA reports built from the daily rollups that are already kept forever.
  • A certificate inventory — every certificate any HTTPS or TLS sensor has seen, sorted by expiry.
  • Remote probes — a second instance reporting into the first, for watching the homelab from outside.
  • A notification digest instead of only event-driven alerts.
  • OIDC login for homelabs that already run an identity provider.
  • An optional Postgres backend for instances that outgrow one SQLite file.

Deliberately out of scope

out of scope

Saying no is most of what keeps this small enough to run on the thing it watches.

  • Agents and infrastructure discovery. ProbeGlass watches what you tell it to watch; it is not a service-discovery or inventory tool.
  • Windows and macOS at all. The container is the only thing that ships; there is no archive to unpack on a desktop.
  • A full SNMP poller. Single OIDs over v2c are in, because that is what a switch, a router or a NAS is asked for. A MIB walk, trap receivers and v3 are not.
  • Multi-tenancy. One instance, one homelab. Several people can have accounts with different roles, but they all see the same sensors — ProbeGlass assumes one group of people who trust each other with the dashboard. Running two containers is the answer to wanting two.
  • Plugins loaded at runtime. The sensor and channel interfaces are the extension point, and they live in the binary where they can be tested.

Suggested

proposals

These are proposals, not promises — nothing here is scheduled, and some of it may never happen.

  • A button in the notification itself. Telegram and Slack can carry a confirmation; asking from a phone beats signing into a dashboard.
  • A migration helper. Somebody moving here with twenty sensors elsewhere would otherwise retype them by hand.
  • Pause a whole group at once. Today it is one sensor at a time, which is the wrong order of operations during a weekend rebuild.
  • A weekly digest as well as event alerts. "Nothing else happened" is the message a quiet system has to be able to send before anybody trusts it.
  • Write the configuration file back out. The reverse direction of a backup: the dashboard emits the YAML it otherwise reads, so the version-controlled part of a setup stops being hand-maintained.
  • A settling time against flapping. A sensor oscillating between two states produces a chain of incidents today; a short hold-down would make it one.
  • Who changed what. The moment more than one account works on an installation, the question is foreseeable.

The rules every item is judged against

These are why the project exists, and they are the reason items on this page are ordered the way they are.

  • One container, no sidecars. A feature that needs a second process to run is not this feature. A small pure-Go library is a different thing: it ships inside the one binary and costs nothing at run time.
  • One SQLite file. A backup stays a file copy.
  • No frontend build step. A change to a .js file is a reload.
  • The numbers must be right. Uptime percentages, gaps and incident durations are the product. Anything that risks double-counting a probe or hiding a gap loses to anything that does not.

Built and released

0.1.0
  • HTTP, TCP (with TLS and a send/expect exchange), ICMP ping and DNS sensors, each validated before it is saved.
  • A dashboard with five views — cards, a list, a tree by site, a wall of heartbeat tiles and a map — live status over SSE, response-time charts, uptime bars, sparklines, an incident timeline, grouping and tags.
  • Three tiers of history: raw for 7 days, hourly for 90 days, daily forever, with exactly one resolution answering any range.
  • An incident lifecycle with retries before an incident opens, reminders while it stays open, recovery alerts, and per-incident acknowledgement.
  • Seven alert channels: Telegram, Discord, Matrix, ntfy, Gotify, Slack, and signed generic webhooks, with custom message templates.
  • First-run setup, bcrypt passwords, an API key, and sensors and channels declared in YAML and re-applied on every start.
  • A multi-arch container image — the only thing it publishes — with a test suite across the store, the configuration, the probe engines and the API.

The rest of 0.1.0

0.1.0

These were built for the same tag rather than a later one, so a container pull gives you everything above and everything below. In the same batch: a top-bar search that reaches sensors, sites, channels, incidents, probe messages and settings; live updates that patch a single card instead of redrawing the dashboard; a Backup and restore panel that writes settings and sensors — and, if you ask, their history — to one JSON file and reads it back; a step-by-step guide inside every alert channel form; and filters on the incident list by status, sensor, period and text.

  • Accounts with roles. Setup creates the first administrator; everyone else is an operator or a viewer.
  • Two-factor authentication per account, with a server-drawn QR code and eight one-time recovery codes shown exactly once.
  • Settings per account, in named tabs. Theme, accent, density, layout, language and interface mode follow the person rather than the installation, and the page shows the one category you chose rather than all of them in a column.
  • A header you build out of widgets. The strip at the top of the dashboard — status ring, uptime, latency, probes, how long it has been monitoring — can be rearranged, added to and emptied: a clock, the recent incidents, the slowest sensors, a small map, a row of shortcuts.
  • A simple and an advanced interface, chosen at setup. Simple hides areas and folds fields; it never disables anything.
  • A guided tour of the dashboard, driven by a data list of steps, that says out loud which data on screen is invented.
  • TLS certificate sensors, reporting the days left and separating a name that does not match, a certificate that has expired, and a chain this host does not trust.
  • Docker container sensors — one read-only call to the Engine API for one container: running, health, restart count.
  • SNMP sensors — one GET of one OID over v2c, checked against a substring or a numeric range.
  • Example data you can take back out and load again, marked as sample data on every card it appears on.
  • probeglass doctor — one command that says what is wrong with an installation and changes nothing.
